## Stages: the lifecycle

A flow declares its state machine in `schema.yaml` as a **`stages:` map** — each stage named
once, with `initial: true` on the entry stage and `terminal: true` on the absorbing ones. An
entity is in exactly one stage at a time, set by a handler's `advances_to` (a single stage,
never a list). Stages are flow-scoped; there is no global stage enum spanning the platform,
and authors never declare a state field on the entity; the runtime exposes it to expressions
as `_entity.current_state` (the `_entity.*` root holds platform metadata; `entity.*` holds
your declared fields). Stages also carry **stage timers**: a `timers:` block on a
stage fires when an entity has sat in it too long, advancing or escalating deterministically.

A flow that declares no `stages:` is **stateless**: it processes events without a lifecycle.
`advances_to` is invalid there. Stateless still allows entities: a handler that writes entity
fields auto-materializes one with no state.

A stage is also where the lifecycle's machinery attaches — each of these is declared on the
stage itself, not scattered through handlers:

- **Stage timers** (`stages.<stage>.timers`) fire when an entity has sat in the stage too
  long — see Timers below.
- **Decision gates** (`stages.<stage>.gate`) pause the stage for a typed human verdict with
  every outcome declared — see [Human in the loop](/concepts/human-in-the-loop).
- **Joins** wait in a stage for a declared set of arrivals, with dedup and timeout owned by
  the platform — see [Parallel work](/build/parallel-work).

## Terminal stages

Terminal stages are absorbing and unconditional. Once an entity is terminal:

- New events targeting it are rejected before any handler runs (outcome `terminal_reject`).
- Its timers are cancelled and its agent sessions terminated.
- All of its state is preserved: queryable, never deleted.

There is no reopen mechanism. To continue work, create a new entity with the relevant data
copied over; the old one stays terminal to preserve the audit trail. Backward transitions to
*non-terminal* stages are allowed — declare a cycle as a
[bounded loop](/build/parallel-work#bounded-loops-declared-revision-cycles) so it carries a
cap and an explicit escape. The prohibition is specifically on leaving a terminal stage.

## Gates

A gate is a named boolean on the entity, set by `sets_gate` and checked by guards. Gates
model "which milestones are complete" in validation-style flows. They default to unset and
are not auto-reset; `clear_gates: true` resets *every* gate on the entity at once (it is
all-or-nothing). Gates are projected by [`flow_scope_key`](/reference/glossary) (a flow's stable
position-based namespace), so they stay stable across instance ids.

## Timers

Time is durable and declarative, in two forms with one owner each.

**Stage timers** are the staged-lifecycle form — declared on the stage, armed when an entity
enters it, cancelled when it leaves:

```yaml schema.yaml
stages:
  awaiting_review:
    timers:
      - after: 48h
        emit: review.sla_escalated       # emit-only: stays in the stage
      - after: "{{marginal_park_days}}d"
        advances_to: expired             # ends the stage: a real lifecycle edge
```

A row with `advances_to` is part of the state machine — reachability analysis and
`describe --graph` see it. This is the canonical form for "an entity sat here too long."

**Node timers** cover what stages cannot anchor: event-triggered delays and boot-anchored
periodic work (a nightly report timer with `start_on: boot`, `recurring: true`). They are
declared on a system node with prefixed triggers (`state:`/`event:`/`boot`); see
[nodes.yaml](/reference/contracts/nodes) for the full form.

Both forms are persisted: a timer survives restart, and one that came due while the process
was down fires on recovery. When any timer fires, its event enters the normal event loop like
any other — timers are just delayed event producers.
