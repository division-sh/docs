## Humans as a first-class actor

Approvals, rejections, and deferrals flow through a durable **mailbox**, using the same event
model as everything else: a pending decision is just another event, waiting for a handler that
happens to be a human. You choose this per transition. A handler runs automatically unless it
adds a `mailbox_write` action (shown below), which pauses it for a human decision; everything
else stays autonomous. We call this: autonomy is a dial, not a switch.

## The mailbox

The mailbox is a persisted, human-in-the-loop task queue. A handler writes an item with the
`mailbox_write` action, declaring the item type, severity (`normal`, `urgent`, `critical`), a
summary, and an explicit payload. Writes are row-idempotent per source event, so a replayed
delivery never creates a duplicate item.

Each item carries a server-built **decision sheet**: the entity context and a preview of
what happens downstream, so an operator can decide without reconstructing the situation by
hand.

```yaml nodes.yaml
# route every refund to a human, unconditionally
refund.requested:
  action:
    id: mailbox_write
    mailbox:
      item_type: approval
      severity: urgent
      summary: "Refund request"
  advances_to: awaiting_approval
```

To make the human step conditional (auto-approve under a limit, human review above it), put
the `action` on a `rules:` branch. The matched rule owns its action; the unmatched branch does
not fire. Both branches run as part of the same atomic handler transaction:

```yaml nodes.yaml
refund.requested:
  rules:
    auto_approve:
      condition: "payload.amount < policy.auto_approval_limit"
      advances_to: approved
    needs_human:
      condition: "payload.amount >= policy.auto_approval_limit"
      advances_to: awaiting_approval
      action:
        id: mailbox_write
        mailbox:
          item_type: approval
          severity: urgent
          summary: "Refund exceeds the auto-approval limit"
```

## Decisions

An operator acts on a pending item in one of three ways:

- **Approve**: emits the configured downstream event, resuming the flow.
- **Reject**: records a reason; no downstream event.
- **Defer**: postpones the item until a given time.

A decided item cannot be decided again (a second attempt returns a conflict). Approvals on
review, approval, and operational-decision items emit `mailbox.item_decided`, which the flow
subscribes to in order to continue.

`mailbox.item_decided` is platform-emitted and **auto-registered**: subscribe to it directly,
no declaration in your own `events.yaml`. (Redeclaring it locally now fails verify with
`platform_namespace_violation`.) The payload carries `mailbox_id`, `mailbox_decision_id`,
`decision` (`approved` | `rejected` | `deferred` | `expired`), `decision_payload`, `item_type`,
`mailbox_payload`, `source_event_id`, `source_flow`, `source_entity_id`, `decided_by`, and
`decided_at`.

```yaml nodes.yaml
# the flow resumes when the operator approves
mailbox.item_decided:
  advances_to: refunding
  emit: refund.issued
```

<Note>
  Branch on `payload.decision` in a `rules:` block (or in a guard) to handle approvals,
  rejections, and deferrals differently. The handler above shows the approve path only.
</Note>

## Budget escalations

Cost control surfaces through the same channel. Token usage is tracked per entity and per
actor; when spend crosses a declared threshold the platform emits
`platform.budget_threshold_crossed` with a `level` (`warning`, `throttle`, `emergency`), and
an emergency raises a mailbox item for a human.
