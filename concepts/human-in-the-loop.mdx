## Humans as a first-class actor

A human decision in Swarm is a typed, durable object — not a chat message and not a webhook
callback. You choose per transition where a human belongs; everything else stays autonomous.
We call this: autonomy is a dial, not a switch.

## Decision gates: pause a stage for a verdict

The primary surface is the **stage gate** — a stage that waits for a typed decision, with
every outcome declared:

```yaml schema.yaml
stages:
  awaiting_launch_approval:
    gate:
      decision: launch_review          # stable audit identity
      context:                         # what the deciding human sees
        staging: entity.staging_url
        qa_summary: entity.qa_summary
      outcomes:
        approve:
          advances_to: operating
          emit: opco.launched
        reject:
          input:
            feedback: {type: text, required: true}   # rejection must say why
          advances_to: building
          emit:
            event: launch.rejected
            fields: {feedback: decision.feedback}
```

When an entity enters the stage, the platform creates a **decision card**: a typed resource
carrying the declared context, the possible verdicts, and any input fields an outcome
requires. Channels (the dashboard, Telegram, whatever renderer you attach) *display* the
card; the decision itself is committed through one API — which means a decision made on your
phone and a decision made in the dashboard are the same object, and the flow resumes
identically. The card's content is hashed, and a verdict must reference the content it saw —
a decision against a stale card is rejected, never silently applied to changed facts.

Every outcome is a declared lifecycle edge: `advances_to` and `emit` are verified statically,
so "what happens if they reject?" has an answer at boot, not at 2am. The platform itself
**never decides** — no timeout auto-approves; an expired card escalates or defers, loudly.

## The mailbox

Alongside gates, the **mailbox** is the persisted queue for human *tasks* — work items that
are not a stage verdict (review this draft, investigate this alert). A handler writes an item
with the `mailbox_write` action, declaring the item type, severity (`normal`, `urgent`,
`critical`), a summary, and an explicit payload. Writes are row-idempotent per source event,
so a replayed delivery never creates a duplicate item.

Each item carries a server-built **decision sheet**: the entity context and a preview of
what happens downstream, so an operator can decide without reconstructing the situation by
hand.

```yaml nodes.yaml
# route a decision to a human instead of proceeding automatically
refund.requested:
  action:
    id: mailbox_write
    mailbox:
      item_type: approval
      severity: urgent
      summary: "Refund exceeds the auto-approval limit"
  advances_to: awaiting_approval
```

## Decisions

An operator acts on a pending item in one of three ways:

- **Approve**: emits the configured downstream event, resuming the flow.
- **Reject**: records a reason; no downstream event.
- **Defer**: postpones the item until a given time.

A decided item cannot be decided again (a second attempt returns a conflict). Approvals on
review, approval, and operational-decision items emit `mailbox.item_decided`, which the flow
subscribes to in order to continue.

To subscribe today, **redeclare** `mailbox.item_decided` in your `events.yaml` with the
platform's payload schema and a `source: external` marker. The redeclaration is required
because the static analyzer treats unfamiliar events as wiring errors; auto-registration of
platform-emitted events is on the roadmap.

```yaml events.yaml
mailbox.item_decided:
  swarm:
    source: external          # platform-emitted; no internal producer to verify
  mailbox_id: text
  mailbox_decision_id: text
  decision: text              # "approved" | "rejected" | "deferred" | "expired"
  decision_payload: text      # operator-supplied approval context (JSON-encoded)
  item_type: text
  mailbox_payload: text       # the original mailbox row payload (JSON-encoded)
  source_event_id: text
  source_flow: text
  source_entity_id: text
  decided_by: text
  decided_at: timestamp
```

Then the handler subscribes and routes the decision:

```yaml nodes.yaml
# the flow resumes when the operator approves
mailbox.item_decided:
  advances_to: refunding
  emit: refund.issued
```

<Note>
  Branch on `payload.decision` in a `rules:` block (or in a guard) to handle approvals,
  rejections, and deferrals differently. The handler above shows the approve path only.
</Note>

## Budget escalations

Cost control surfaces through the same channel. Token usage is tracked per entity and per
actor; when spend crosses a declared threshold the platform emits
`platform.budget_threshold_crossed` with a `level` (`warning`, `throttle`, `emergency`), and
an emergency raises a mailbox item for a human.
