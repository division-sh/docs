Say twenty startups arrive in one event and each needs its own agent to investigate it. You
**fan out** one event per startup, each startup gets its own flow instance with its own
agent, and a **join** collects the results and says when they're all in. You declare how to
split and what counts as done; the platform owns dispatch, duplicates, and deadlines. No
counters, no polling, no shared state.

## Fan out: one event per item

```yaml scout/nodes.yaml
startups.found:
  fan_out:
    items_from: payload.startups
    as: lead
    identity: lead.startup_id       # stable identity per item
    max_items: 25
    emit:
      event: startup.discovered
      fields:
        startup_id: lead.startup_id
        name: lead.name
  data_accumulation:
    writes:
      - target_field: startup_ids   # remember the membership for the join
        expression: payload.startups.map(s, s.startup_id)
      - target_field: batch_id
        expression: payload.batch_id
```

`identity` names the stable per-item key; `max_items` bounds the fan-out. Record the member
list (and a window key, such as a batch id) in entity fields — the join below reads them. A
**window** groups arrivals into one batch — here, every result carrying the same `batch_id`
counts toward the same join.

## One instance per item

The receiving flow declares its identity once, and instances mint themselves on first
delivery — there is no creation call:

```yaml flows/matcher/schema.yaml
name: matcher
mode: template
instance: startup_id                # one instance per startup_id
stages:
  investigating:
    initial: true
  assessed:
    terminal: true
pins:
  inputs:
    events:
      - name: startup_discovered
        event: startup.discovered
        resolution:
          mode: select-or-create    # first event for a new startup_id mints the instance
        carries:
          startup_id: {from: payload.startup_id, type: text}
```

Every selecting input pin must carry a field named after `instance:`; the pin's instance key
derives from it. Each instance materializes **its own copy** of the flow's declared agents —
one live agent per (agent declaration, instance) pair — so one instance finishing never
affects a sibling's agent, and `memory: true` agents get one conversation per instance.

## Fan in: the barrier join

Convergence is owned by two declarations on the collecting flow: a **fan-in resolution pin**
(which events count, how they deduplicate, which window they belong to) and a staged **`join:`
row** (membership, completion, timeout):

```yaml scout/schema.yaml (input pin)
- name: assessed_reported
  event: startup.assessed
  resolution:
    mode: fan-in
    aggregation: barrier
    window: payload.batch_id        # arrivals group by window
    dedup_by: payload.startup_id    # a redelivery never double-counts
    singleton: scout                # the collecting instance
  carries:
    startup_id: {from: payload.startup_id, type: text}
    batch_id: {from: payload.batch_id, type: text}
```

```yaml scout/nodes.yaml (join row)
startup.assessed:
  join:
    stage: awaiting                 # the stage that waits
    members:
      by: payload.startup_id        # which payload field identifies the arriving member
      from: entity.startup_ids      # who must arrive (written at fan-out time)
    window:
      by: payload.batch_id          # which payload field names the window
      from: entity.batch_id
    output: payload.match_score     # the value captured from each arrival (required)
    on_complete:
      data_accumulation:
        writes:
          - target_field: top_score
            expression: "join.results.max()"   # aggregate over the collected outputs
      advances_to: reported
    timeout:                        # required — bare joins are invalid
      after: 30m
      advances_to: partial_report
```

The join arms when the entity enters the waiting stage. It settles exactly once per window —
on completion or on timeout, whichever comes first. Two aggregation modes exist:

| Mode | Delivers | Use when |
|---|---|---|
| `barrier` (shown here) | once, when the window completes | you only need the finished set |
| `stream` | every deduplicated arrival as it comes, and still tracks window completion | the collector should react per result (progress updates, incremental writes); see [`examples/routing/fan-in/stream`](https://github.com/division-sh/swarm/tree/master/examples/routing/fan-in/stream) |

<Warning>
  Do **not** hand-roll this with `accumulate` and an `expected_count` comparison: that
  pattern has no dedup, no timeout, and deadlocks when the last result arrives before the
  expected count is written.
</Warning>

The canonical runnable version of this whole shape is [`examples/routing/fan-in/barrier`](https://github.com/division-sh/swarm/tree/master/examples/routing/fan-in/barrier).

## The singleton coordinator

When many template instances need **shared state** — a rate budget, an aggregate score, a
cross-instance learning table — that state gets one owner: a `mode: singleton` coordinator
flow whose entity holds it as **typed contained map/list fields**. Instances report to the
coordinator through ordinary events (often the fan-in pin above); the coordinator's handlers
update the contained state deterministically.

```yaml
# flows/coordinator/schema.yaml
mode: singleton              # one instance for the whole system
# flows/coordinator/entities.yaml
budget:
  scores: [LeadScore]        # typed contained state with one owner
```

Two rules:

- Items in that contained state have no lifecycle of their own — no timers, retries, or
  terminal stage. If an item needs those, promote it to a template instance.
- The coordinator role is explicit — a plain `mode: static` flow does not qualify.

## Bounded loops: declared revision cycles

When work legitimately cycles — draft, review, revise, review again — the cycle is declared,
capped, and given an explicit exit. Declare the cycle with `loops:` rather than hand-rolling
a counter in a guard:

```yaml nodes.yaml
loops:
  revision:
    revision_field: revision_id     # the event field carrying the current revision identity
    max_attempts: "{{policy.inner_revision_max}}"
    escape:                         # reaching the cap is a declared outcome, not a failure
      advances_to: escalated
      emit:
        event: review.escalated
        fields:
          revision_id: {cel: loop.revision_id}

event_handlers:
  work.started:
    loop: {start: revision, from: queued}
    advances_to: drafting
  draft.ready:
    loop: {admit: revision, from: drafting}
    advances_to: review
  review.revision_requested:
    loop: {repeat: revision, from: review}   # below the cap: new revision, back to drafting
    advances_to: drafting
  review.approved:
    loop: {close: revision, from: review}
    advances_to: approved
```

Four operations cover a loop's life: `start` creates the loop's durable record at attempt 1, `admit`
accepts work for the current revision, `repeat` increments the attempt and mints a new
revision (or, at the cap, atomically takes the declared `escape`), and `close` exits the
region. `max_attempts` is evaluated once at start and stamped into the activation — editing
policy mid-run never changes an active loop's cap, and replay sees the same cap the run did.
Every operation declares its exact `from:` stage; the runtime accepts no inferred source.

Verify checks the loop's shape statically: one `start` from outside the cycle, at least one
`repeat` and `close`, an escape target outside the cycle, and every handler inside the cycle
declaring its loop operation. Nested and unbounded loops are rejected.

## Stage timers: time as a lifecycle edge

Both shapes above compose with **stage timers** — one-shot temporal rows declared on the
stage itself:

```yaml schema.yaml
stages:
  awaiting_review:
    timers:
      - after: 48h
        emit: review.sla_escalated      # emit-only: stays in the stage
      - after: "{{marginal_park_days}}d"
        advances_to: expired            # advances: ends the stage
```

A timer arms when the entity enters the stage and cancels when it leaves. A row with
`advances_to` is a real lifecycle edge — reachability analysis and `describe --graph` see it.
