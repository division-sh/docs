A handler continues the flow by emitting the next event. An emitted event's payload is
**producer-complete**: the handler must populate every field the event declares, through
`emit.fields`. Nothing is copied automatically from the triggering event, and there are no
defaults. Each entry in `fields` is a CEL expression, usually reading the entity you just wrote
or the incoming `payload`:

```yaml
ticket.classified:
  advances_to: assigned
  emit:
    event: ticket.assigned        # declares fields: category, priority
    fields:
      category: entity.category   # read the fields this handler just wrote
      priority: entity.priority
```

The bare string form, `emit: ticket.assigned`, emits with an **empty** payload. The analyzer
accepts it, so the empty payload only shows up at runtime when a subscriber receives `{}`. Use
the bare form only for events that declare no fields; use `fields` the moment an event carries
data.

## Routing is not the producer's job

An emit carries **no routing authority**. The producer says *what happened*; who receives it
is owned entirely by the receiving side:

- **Inside a flow** — delivery comes from subscriptions (`subscribes_to` on nodes, `subscriptions`
  on agents). An internal emit needs nothing beyond `event` and `fields`.
- **Across flows** — the event leaves through a **declared output pin**, the parent package
  binds it with a `connect` edge, and the *receiver's* input pin owns instance selection via
  `resolution` and its declared `carries`. See [Composing flows](/build/composition).
- **Replies** — reply correlation is declared on the receiving pin, not chosen per-emit by the
  producer.

Older Swarm versions accepted `emit.target` and `emit.broadcast` — producer-side recipient and
cardinality selection. Both are retired and now fail at load with a `RETIRED-EMIT-ROUTING`
error naming the replacement. If you are migrating: a `target: sender` reply becomes
receiver-owned reply correlation on the pin; a `broadcast: true` fan-out becomes either
ordinary subscriptions (every subscriber in the flow already receives an internal event) or
explicit `connect` edges per receiving flow.

A handler's top-level `emit` is valid only when the handler has a single emit site. If the
handler also branches with `rules` or `on_complete`, the emit moves onto the branch; a
handler-level `emit` alongside `rules` is a boot error. See [Branching](/build/handlers/branching).
